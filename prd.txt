## 1. Executive Summary

Bia is a pan-African payment interoperability and settlement infrastructure designed to solve the fragmentation, cost, and unreliability of cross-border payments across the African continent. Africa's cross-border payments market was worth **$329 billion in 2025** and is projected to reach **$1 trillion by 2035** . Yet Sub-Saharan Africa remains the world's most expensive remittance region, with the average cost of sending $200 hovering between **7% and 9%** — more than double the global target of 3% .

Bia is not a consumer app. It is an **API-first infrastructure layer** that:

- Abstracts 50+ African payment providers (mobile money, bank rails, cards) behind a single unified API.
- Uses an **AI-powered routing engine** to select the optimal payment rail in real time based on cost, speed, liquidity, and compliance requirements.
- Uses **regulated stablecoins** (USDC, USDT) as the cross-border settlement backbone to enable near-instant, 24/7 transfers.
- Provides a **deterministic policy engine** that validates every transaction before execution, ensuring AI never directly authorizes fund movement.
- Includes **full UI surfaces** for merchants, developers, operations teams, and partners.
- Exposes an **MCP (Model Context Protocol) server** that allows AI agents to initiate payments via natural language.

The target market is B2B2C: pan-African SMEs, global freelance platforms, fintechs, and neobanks that need reliable cross-border payment infrastructure without building it themselves.


## 2. Vision & Strategic Context

### 2.1 The Core Insight

Africa's payment ecosystem is not lacking in rails. It is lacking in **interoperability**. There are over **860 million mobile money accounts** globally, with Africa accounting for over 70% of transaction value. M-PESA, MTN MoMo, Airtel Money, Orange Money, and dozens of other wallets process billions of transactions annually. Yet these systems largely cannot talk to each other or connect to global commerce.

The winning approach is not to build another wallet. It is to build the **switching and settlement layer** that connects existing rails to each other and to the global economy.

### 2.2 Strategic Position

Bia occupies the space between:
- **Mobile money operators** (M-PESA, MTN MoMo, Airtel Money) — who dominate local payments but have limited cross-border capability.
- **Global payment platforms** (PayPal, Stripe, Wise) — who have global reach but struggle with African regulatory fragmentation and mobile-money-native users.
- **Pan-African processors** (Flutterwave, Paystack, PawaPay) — who excel at merchant acquiring but have not fully cracked seamless interoperability between local wallets and stablecoin settlement.

The strategic moat is the **compliance orchestration layer** — the automated routing of KYC/AML rules across 54 regulatory jurisdictions — which is the hardest component to build and the most defensible.

## 4. Target Users & Personas

### 4.1 Primary Users (B2B2C)

**Persona 1: Pan-African SME Merchant**
- **Profile:** A Lagos-based e-commerce business selling to customers in Ghana, Kenya, and Nigeria.
- **Pain:** Cannot accept payments from customers using different mobile money wallets. Each integration takes weeks.
- **Need:** A single API to accept payments from any African payment method.

**Persona 2: Global Freelance Platform**
- **Profile:** A US-based platform paying 50,000 African freelancers monthly.
- **Pain:** PayPal freezes accounts. Bank transfers take 5–7 days and cost $15–30 per transfer.
- **Need:** A payout API that sends funds to mobile money wallets in minutes.

**Persona 3: African Fintech / Neobank**
- **Profile:** A Kenyan neobank with 200,000 users that wants to offer cross-border payments.
- **Pain:** Building and maintaining integrations with 10+ payment providers is expensive and time-consuming.
- **Need:** A single integration that gives access to all African payment rails.

### 4.2 Secondary Users (End Consumers)

- African freelancers receiving payments from global clients.
- Individuals sending money to family across African borders.
- Creators monetizing content globally and withdrawing to local wallets.

### 4.3 Internal Users

- **Operations Team:** Monitors transactions, resolves stuck payments, manages liquidity.
- **Compliance Team:** Reviews flagged transactions, files SARs, handles regulatory inquiries.
- **Treasury Team:** Manages stablecoin reserves, FX positions, and corridor liquidity.
- **Developer Support:** Assists B2B clients with integration issues.

### 5.3 Communication Patterns

- **Synchronous:** REST/JSON over HTTPS for client-facing APIs. gRPC for inter-service communication.
- **Asynchronous:** Kafka for event streaming, webhooks for client notifications.
- **Event Sourcing:** All state changes emit domain events to Kafka. Ledger is event-sourced.
- **Idempotency:** All API endpoints accept an `Idempotency-Key` header. Duplicate requests return the original result.


## 6. Module 1: Unified Payment API Gateway

The API Gateway is the single entry point for all client requests. It handles authentication, rate limiting, request validation, and routing to the appropriate backend service.

### 6.3 Authentication

- **OAuth 2.0:** Client credentials flow for server-to-server.
- **API Keys:** For simple integrations. Prefix: `ap_`.
- **JWT:** For dashboard sessions. RS256 signed, 15-minute expiry.
- **HMAC:** Webhook signature verification using SHA-256.

### 6.4 Rate Limiting

| Tier | Requests/minute | Burst |
|---|---|---|
| Free | 60 | 100 |
| Growth | 600 | 1,000 |
| Scale | 6,000 | 10,000 |
| Enterprise | Custom | Custom |

Rate limit headers returned: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`. On exceeding: HTTP 429 with `Retry-After` header.

### 6.5 Idempotency

All POST/PUT endpoints require an `Idempotency-Key` header. Keys are valid for 24 hours. Duplicate requests within the window return the original response with a `Idempotent-Replay: true` header.

### 6.6 Error Handling

| HTTP Code | Error Code | Description |
|---|---|---|
| 400 | `invalid_request` | Malformed request |
| 401 | `unauthorized` | Invalid API key |
| 403 | `forbidden` | Insufficient permissions |
| 404 | `not_found` | Resource not found |
| 409 | `conflict` | Duplicate idempotency key with different payload |
| 422 | `validation_error` | Business logic validation failed |
| 429 | `rate_limit_exceeded` | Too many requests |
| 500 | `internal_error` | Server error |
| 503 | `service_unavailable` | Temporary outage |

**Error Response Format:**
```json
{
  "error": {
    "code": "validation_error",
    "message": "Amount exceeds maximum for this payment method",
    "details": [
      {
        "field": "amount",
        "issue": "exceeds_max",
        "max": 250000
      }
    ],

  }
}
```


## 7. Module 2: Provider Adapter Layer (Connectors)

### 7.1 Purpose

Each payment provider has its own API, authentication method, data format, and quirks. The Provider Adapter Layer isolates this complexity into independent microservices, each specialized for one provider. This allows the core system to treat all providers uniformly.

### 7.2 Supported Providers (Phase 1)

| Provider | Type | Countries | API Style | Auth |
|---|---|---|---|---|
| M-PESA (Daraja) | Mobile Money | Kenya, Tanzania, DRC, Ghana | REST + SOAP | OAuth 2.0 + API Key  |
| MTN MoMo | Mobile Money | 15+ countries | REST | OAuth 2.0 + Subscription Key  |
| Airtel Money | Mobile Money | 14 countries | REST | OAuth 2.0 |
| PawaPay | Aggregator | 20 countries | REST | API Key  |
| Paystack | Card + Bank | Nigeria, Ghana, SA, Kenya | REST | Bearer Token |
| Flutterwave | Card + Bank + Mobile Money | 30+ countries | REST | OAuth 2.0 |
| Bank Transfer (NIBSS, NIP) | Bank Rail | Nigeria | REST | OAuth 2.0 |
| Stablecoin (USDC/USDT) | Blockchain | Global | JSON-RPC | Wallet Signature |

### 7.3 Adapter Interface

Every adapter must implement the following interface:

```typescript
interface PaymentAdapter {
  // Provider metadata
  getProviderInfo(): ProviderInfo;

  // Collections (accept payments)
  initiateCollection(request: CollectionRequest): Promise<CollectionResponse>;
  getCollectionStatus(providerRef: string): Promise<CollectionStatus>;
  refundCollection(providerRef: string, amount?: number): Promise<RefundResponse>;

  // Disbursements (send payments)
  initiateDisbursement(request: DisbursementRequest): Promise<DisbursementResponse>;
  getDisbursementStatus(providerRef: string): Promise<DisbursementStatus>;

  // Health check
  checkHealth(): Promise<HealthStatus>;

  // Webhook parsing
  parseWebhook(payload: unknown, headers: Record<string, string>): WebhookEvent;
}
```

### 7.4 Adapter Details

#### 7.4.1 M-PESA Daraja Adapter

**Authentication:**
- OAuth 2.0 bearer token (expires every hour).
- Consumer Key + Consumer Secret from Safaricom Developer Portal .
- Passkey for STK Push.

**Key Operations:**
- **STK Push (Lipa Na M-PESA Online):** Initiates a payment prompt on the customer's phone.
- **C2B (Customer to Business):** Registers validation and confirmation URLs.
- **B2C (Business to Customer):** Sends money to a customer's M-PESA wallet.
- **Transaction Status:** Queries the status of a transaction.
- **Reversal:** Reverses a completed transaction.

**Endpoint:** `https://api.safaricom.co.ke/mpesa/stkpush/v1/processrequest`

**Callback Handling:** M-PESA sends callbacks to a publicly reachable HTTPS URL. The adapter must validate the callback signature and update the transaction status.

**Rate Limits:** 100 requests/minute (production).

#### 7.4.2 MTN MoMo Adapter

**Authentication:**
- OAuth 2.0 with Subscription Key.
- API User + API Key creation via `POST /v1_0/apiuser`.

**Key Operations:**
- **Request to Pay:** Initiates a payment request.
- **Transfer:** Sends money to a user.
- **Account Balance:** Queries account balance.
- **User Info:** Retrieves user KYC information.

**Endpoint:** `https://proxy.momoapi.mtn.com` (production) 

**Sandbox:** `https://sandbox.momodeveloper.mtn.com` 

#### 7.4.3 PawaPay Adapter

PawaPay provides a single API to connect to nearly 50 mobile money operators across 20 African countries .

**Key Operations:**
- **Deposits:** Collect payments from mobile money wallets.
- **Payouts:** Send funds to mobile money wallets.
- **Refunds:** Reverse a deposit.
- **Payment Pages:** Hosted checkout pages.

**Endpoint:** `https://api.pawapay.io/v2`

**Webhook:** PawaPay sends webhook callbacks for deposit and payout status changes.

#### 7.4.4 Stablecoin Settlement Adapter

**Networks:** Ethereum (USDC, USDT), Polygon (USDC), Solana (USDC), Aptos (USDC).

**Operations:**
- **Generate Deposit Address:** Create a unique address for a user.
- **Initiate Transfer:** Send stablecoins to an external address.
- **Check Balance:** Query on-chain balance.
- **Monitor Incoming Transactions:** Watch for incoming transfers.

**Key Management:** Uses HashiCorp Vault for private key storage. Multi-signature wallets for treasury operations. Hardware Security Modules (HSMs) for signing.

**Compliance:** Every stablecoin transaction is screened against sanctions lists and KYT (Know Your Transaction) providers before execution.

### 7.5 Fallback & Circuit Breaker

Each adapter implements a circuit breaker pattern. If a provider's API failure rate exceeds 10% over a 5-minute window, the circuit breaker opens and the adapter is marked as `unavailable`. The AI Routing Engine will route transactions to alternative providers until the circuit closes.

**Health Check:** Every adapter exposes a `/health` endpoint that checks:
- API connectivity.
- Authentication token validity.
- Recent transaction success rate.
- Response latency.

### 7.6 Provider Certification

Each adapter must pass a certification suite before going to production:

| Test | Description |
|---|---|
| **Happy Path** | Successful collection and disbursement |
| **Failure Handling** | Provider returns error; system handles gracefully |
| **Timeout** | Provider does not respond; system times out and retries |
| **Webhook Parsing** | Correct parsing of all webhook event types |
| **Idempotency** | Duplicate requests do not result in double charges |
| **Rate Limiting** | System respects provider rate limits |
| **Currency Handling** | Correct handling of different currencies |
| **Reversal** | Successful reversal of a completed transaction |


## 8. Module 3: AI Intent & Routing Engine

### 8.1 Purpose

The AI Intent & Routing Engine is the **intelligence layer** of AetherPay. It performs two functions:

1. **Intent Extraction:** Parse natural language requests into structured payment intents.
2. **Routing Recommendation:** Recommend the optimal payment rail based on real-time constraints.

**Critical Design Principle:** The AI **never** authorizes a payment. It extracts intent and recommends a route. All authorization decisions are made by the Deterministic Policy Engine (Module 4).

### 8.2 Architecture

## 9. Module 4: Deterministic Policy & Compliance Engine

### 9.1 Purpose

The Deterministic Policy Engine is the **safety gate** between AI intent and payment execution. It is implemented in pure, deterministic code (no LLM, no probabilistic inference). It validates every payment intent against a configurable set of rules before the transaction is allowed to proceed.

**Core Principle:** The Policy Engine **fails closed**. If there is any doubt, the transaction is rejected or escalated for human review. The IMF explicitly recommends this architecture: a "deterministic control safety gate between intent formation and execution" .

### 9.2 Policy Rules

#### 9.2.1 Amount Limits

| Rule | Description | Action |
|---|---|---|
| `max_transaction_amount` | Maximum single transaction amount per corridor | Reject if exceeded |
| `daily_limit` | Maximum total daily amount per user | Reject if exceeded |
| `monthly_limit` | Maximum total monthly amount per user | Reject if exceeded |
| `velocity_check` | Maximum transactions per hour/day | Reject if exceeded |

#### 9.2.2 KYC Tier Validation

| KYC Tier | Max Transaction | Max Daily | Max Monthly |
|---|---|---|---|
| Tier 0 (Unverified) | $0 | $0 | $0 |
| Tier 1 (Basic) | $500 | $1,000 | $5,000 |
| Tier 2 (Verified) | $5,000 | $10,000 | $50,000 |
| Tier 3 (Enhanced) | $50,000 | $100,000 | $500,000 |

#### 9.2.3 Sanctions & Watchlist Screening

Every transaction is screened against:
- OFAC SDN List
- UN Consolidated Sanctions List
- EU Sanctions List
- Local sanctions lists (per jurisdiction)
- PEP (Politically Exposed Persons) lists

Screening is performed **before** the transaction is allowed to proceed. A match results in immediate rejection and escalation to the Compliance team.

#### 9.2.4 Corridor Availability

Each corridor has a set of enabled rails. If no rail is available for a corridor, the transaction is rejected with a clear error message.

#### 9.2.5 Intent Verification

The Policy Engine verifies that the AI's extracted intent matches the user's original input. This is done by:
1. Comparing the extracted fields against the original message.
2. Flagging any discrepancies (e.g., AI extracted $500 but user said $50).
3. Escalating ambiguous cases to human review.

### 9.3 Policy Engine Implementation

```typescript
interface PolicyRule {
  id: string;
  name: string;
  description: string;
  evaluate(context: PolicyContext): PolicyResult;
}

interface PolicyContext {
  intent: PaymentIntent;
  user: UserProfile;
  corridor: CorridorConfig;
  timestamp: Date;
  recentTransactions: Transaction[];
}

interface PolicyResult {
  decision: 'APPROVE' | 'REJECT' | 'ESCALATE';
  ruleId: string;
  reason: string;
  metadata?: Record<string, unknown>;
}

class PolicyEngine {
  private rules: PolicyRule[];

  evaluate(context: PolicyContext): PolicyDecision {
    const results: PolicyResult[] = [];

    for (const rule of this.rules) {
      const result = rule.evaluate(context);
      results.push(result);

      // Fail closed: any REJECT stops evaluation
      if (result.decision === 'REJECT') {
        return {
          decision: 'REJECT',
          results,
          primaryReason: result.reason,
        };
      }

      // ESCALATE: continue evaluation but flag for review
      if (result.decision === 'ESCALATE') {
        // Log and continue
      }
    }

    // If any ESCALATE, return ESCALATE
    const escalations = results.filter(r => r.decision === 'ESCALATE');
    if (escalations.length > 0) {
      return {
        decision: 'ESCALATE',
        results,
        primaryReason: escalations[0].reason,
      };
    }

    return {
      decision: 'APPROVE',
      results,
    };
  }
}
```

### 9.4 Policy Configuration

Policies are stored in a database and can be updated without code deployment. Each policy has:
- `id`: Unique identifier
- `name`: Human-readable name
- `description`: Description of the policy
- `priority`: Evaluation order (lower = earlier)
- `enabled`: Boolean
- `config`: JSON configuration
- `effective_from`: Start date
- `effective_to`: End date (optional)

**Policy Changes:** All policy changes are versioned and audited. A change requires approval from two team members (four-eyes principle).

## 10. Module 5: Ledger & Reconciliation Service

### 10.1 Purpose

The Ledger Service is the **single source of truth** for all money movement within Bia. It is a **double-entry, append-only ledger** that records every transaction as a balanced set of debits and credits . Without a proper ledger, a payment platform cannot answer the most basic question: "Where is the money right now?"

### 10.2 Double-Entry Accounting Model

Every transaction creates at least two ledger entries:

| Entry | Account | Debit | Credit |
|---|---|---|---|
| 1 | Customer Wallet (Liability) | $100 | |
| 2 | Settlement Account (Asset) | | $100 |

The sum of all debits must equal the sum of all credits at all times.

### 10.3 Account Types

| Account Type | Description | Normal Balance |
|---|---|---|
| **Asset** | Funds held by AetherPay (settlement accounts, stablecoin reserves) | Debit |
| **Liability** | Funds owed to customers (customer wallets, merchant balances) | Credit |
| **Revenue** | Fees earned by AetherPay | Credit |
| **Expense** | Costs incurred by AetherPay (provider fees, FX costs) | Debit |
| **Equity** | Owner's equity | Credit |

### 10.5 Ledger Operations

#### 10.5.1 Record Transaction

```typescript
async function recordTransaction(
  transaction: TransactionRequest
): Promise<TransactionResult> {
  // Start a database transaction
  return await db.transaction(async (trx) => {
    // 1. Validate idempotency key
    const existing = await trx('idempotency_keys')
      .where({ key: transaction.idempotencyKey })
      .first();

    if (existing) {
      return JSON.parse(existing.response_body);
    }

    // 2. Calculate fee
    const fee = calculateFee(transaction);
    const netAmount = transaction.amount - fee;

    // 3. Create transaction record
    const [txn] = await trx('transactions')
      .insert({
        reference: transaction.reference,
        type: transaction.type,
        status: 'pending',
        amount: transaction.amount,
        currency: transaction.currency,
        fee,
        net_amount: netAmount,
        sender_id: transaction.senderId,
        recipient_id: transaction.recipientId,
        provider: transaction.provider,
        metadata: transaction.metadata,
      })
      .returning('*');

    // 4. Create journal entries (double-entry)
    // Debit: Customer Wallet (Liability decreases)
    await trx('journal_entries').insert({
      transaction_id: txn.id,
      account_id: await getAccountId('customer_wallet', transaction.senderId),
      debit_amount: transaction.amount,
      currency: transaction.currency,
      description: `Payment from ${transaction.senderId}`,
    });

    // Credit: Settlement Account (Asset increases)
    await trx('journal_entries').insert({
      transaction_id: txn.id,
      account_id: await getAccountId('settlement_account', transaction.currency),
      credit_amount: transaction.amount,
      currency: transaction.currency,
      description: `Settlement for ${txn.reference}`,
    });

    // Credit: Revenue Account (Fee earned)
    await trx('journal_entries').insert({
      transaction_id: txn.id,
      account_id: await getAccountId('revenue', 'fee'),
      credit_amount: fee,
      currency: transaction.currency,
      description: `Fee for ${txn.reference}`,
    });

    // Debit: Expense Account (Provider cost)
    await trx('journal_entries').insert({
      transaction_id: txn.id,
      account_id: await getAccountId('expense', 'provider_fee'),
      debit_amount: fee * 0.6, // Example: 60% of fee is provider cost
      currency: transaction.currency,
      description: `Provider cost for ${txn.reference}`,
    });

    // 5. Store idempotency key
    await trx('idempotency_keys').insert({
      key: transaction.idempotencyKey,
      request_hash: hashRequest(transaction),
      response_body: JSON.stringify({ id: txn.id, status: 'pending' }),
      expires_at: new Date(Date.now() + 24 * 60 * 60 * 1000),
    });

    return { id: txn.id, status: 'pending' };
  });
}
```

#### 10.5.2 Get Balance

```sql
-- Get balance for an account
SELECT 
    a.code,
    a.name,
    a.type,
    a.currency,
    COALESCE(SUM(je.debit_amount), 0) AS total_debits,
    COALESCE(SUM(je.credit_amount), 0) AS total_credits,
    CASE 
        WHEN a.type IN ('asset', 'expense') THEN 
            COALESCE(SUM(je.debit_amount), 0) - COALESCE(SUM(je.credit_amount), 0)
        ELSE 
            COALESCE(SUM(je.credit_amount), 0) - COALESCE(SUM(je.debit_amount), 0)
    END AS balance
FROM accounts a
LEFT JOIN journal_entries je ON je.account_id = a.id
WHERE a.id = $1
GROUP BY a.id;
```

### 10.6 Reconciliation

Reconciliation is the process of verifying that AetherPay's internal ledger matches the external records of payment providers and banks.

**Reconciliation Types:**

| Type | Frequency | Description |
|---|---|---|
| **T+0 Streaming** | Real-time | Webhook events are reconciled against ledger entries as they arrive. |
| **T+1 File-Based** | Daily | Provider settlement files are downloaded and matched against ledger entries. |
| **T+7 Hash Verification** | Weekly | Cryptographic hashes are exchanged with providers to verify transaction integrity. |

**Break Detection:** Any discrepancy between the ledger and external records is flagged as a "break." Breaks are categorized:
- **Timing Break:** Transaction is recorded in one system but not the other yet. Resolves automatically.
- **Amount Break:** Transaction amount differs. Requires investigation.
- **Missing Transaction:** Transaction exists in one system but not the other. Requires investigation.

**Operator UI:** The Admin Console provides a reconciliation dashboard where operators can view breaks, investigate, and resolve them.

### 11.5 Key Management

| Key Type | Storage | Signing | Rotation |
|---|---|---|---|
| **Hot Wallet** | AWS KMS / HashiCorp Vault | Automated | Every 30 days |
| **Warm Wallet** | HSM (Hardware Security Module) | Multi-sig (2-of-3) | Every 90 days |
| **Cold Wallet** | Air-gapped HSM | Multi-sig (3-of-5) | Every 180 days |

**Transaction Signing Flow:**
1. Transaction is initiated by the Settlement Service.
2. Transaction details are sent to the HSM for signing.
3. HSM validates the transaction against policy rules (amount limits, destination whitelist).
4. HSM signs the transaction and returns the signature.
5. Signed transaction is broadcast to the network.

### 11.6 Compliance for Stablecoins

Stablecoin transactions are subject to the same AML/KYC requirements as fiat transactions. Additionally:

- **KYT (Know Your Transaction):** Every on-chain transaction is screened using a KYT provider (e.g., Chainalysis, Elliptic) to assess source-of-funds and scam risk.
- **Sanctions Screening:** Destination addresses are screened against OFAC and other sanctions lists.
- **Travel Rule:** For transactions above $1,000, originator and beneficiary information is transmitted to the receiving VASP (Virtual Asset Service Provider).

## 14. Module 9: MCP Server for AI Agents

### 14.1 Purpose

The MCP (Model Context Protocol) Server allows AI agents (Claude, ChatGPT, Cursor, etc.) to initiate payments via natural language. This is the **AI-native interface** for AetherPay.

MCP is a protocol that standardizes communication between LLM clients and server-hosted tools . By exposing payment operations as MCP tools, any MCP-compatible AI agent can become a payment terminal.

### 14.2 MCP Tools

| Tool | Description | Parameters |
|---|---|---|
| `initiate_payment` | Initiate a payment (collection or disbursement) | `amount`, `currency`, `recipient`, `method` |
| `check_payment_status` | Check the status of a payment | `payment_id` |
| `get_balance` | Get the balance of an account | `currency` |
| `list_transactions` | List recent transactions | `limit`, `offset`, `filters` |
| `get_exchange_rate` | Get FX rate between two currencies | `from`, `to` |
| `validate_recipient` | Validate a recipient's phone number | `phone_number`, `provider` |
| `get_fee_estimate` | Get fee estimate for a payment | `amount`, `currency`, `method` |

### 14.3 MCP Server Implementation

```typescript
import { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js';
import { StdioServerTransport } from '@modelcontextprotocol/sdk/server/stdio.js';
import { z } from 'zod';

const server = new McpServer({
  name: 'aetherpay',
  version: '1.0.0',
});

// Tool: Initiate Payment
server.tool(
  'initiate_payment',
  {
    amount: z.number().positive(),
    currency: z.string().length(3),
    recipient: z.object({
      phoneNumber: z.string(),
      provider: z.enum(['mpesa', 'mtn_momo', 'airtel_money']),
      country: z.string().length(2),
    }),
    description: z.string().optional(),
  },
  async ({ amount, currency, recipient, description }) => {
    // 1. Extract intent (deterministic)
    const intent = {
      type: 'disbursement',
      amount,
      currency,
      recipient,
      description,
    };

    // 2. Validate via Policy Engine (deterministic)
    const validation = await policyEngine.evaluate(intent);

    if (validation.decision === 'REJECT') {
      return {
        content: [{
          type: 'text',
          text: `Payment rejected: ${validation.primaryReason}`,
        }],
      };
    }

    // 3. Get routing recommendation (AI advisory)
    const recommendation = await routingRecommender.recommend(intent);

    // 4. Validate route (deterministic)
    const routeValidation = await validateRoute(recommendation);

    if (!routeValidation.valid) {
      return {
        content: [{
          type: 'text',
          text: `Route validation failed: ${routeValidation.reason}`,
        }],
      };
    }

    // 5. Execute payment
    const payment = await paymentService.disburse(intent, routeValidation.rail);

    return {
      content: [{
        type: 'text',
        text: `Payment initiated. ID: ${payment.id}. Status: ${payment.status}. Route: ${routeValidation.rail}. Expected settlement: ${payment.expectedSettlement}.`,
      }],
    };
  }
);

// Tool: Check Payment Status
server.tool(
  'check_payment_status',
  { paymentId: z.string() },
  async ({ paymentId }) => {
    const payment = await paymentService.getStatus(paymentId);
    return {
      content: [{
        type: 'text',
        text: `Payment ${payment.id}: ${payment.status}. Amount: ${payment.amount} ${payment.currency}. Settled: ${payment.settledAt || 'pending'}.`,
      }],
    };
  }
);

// Tool: Get Balance
server.tool(
  'get_balance',
  { currency: z.string().length(3).optional() },
  async ({ currency }) => {
    const balances = await accountService.getBalances(currency);
    return {
      content: [{
        type: 'text',
        text: `Balances: ${balances.map(b => `${b.amount} ${b.currency}`).join(', ')}`,
      }],
    };
  }
);

// Start server
const transport = new StdioServerTransport();
await server.connect(transport);
```

### 14.4 MCP Client Configuration

Users can connect AetherPay's MCP server to their AI client (e.g., Claude Desktop) by adding the following to their configuration:

```json
{
  "mcpServers": {
    "aetherpay": {
      "command": "npx",
      "args": ["-y", "@aetherpay/mcp-server"],
      "env": {
        "AETHERPAY_API_KEY": "ap_live_...",
        "AETHERPAY_ENVIRONMENT": "production"
      }
    }
  }
}
```

Once configured, the user can type:

> *"Send KES 5,000 to Mary's M-PESA number +254712345678."*

The AI agent will:
1. Call the `initiate_payment` tool.
2. The tool will validate the request via the Policy Engine.
3. The tool will execute the payment via the appropriate rail.
4. The AI agent will respond with a confirmation.

### 14.5 Security for MCP

| Concern | Mitigation |
|---|---|
| **Prompt Injection** | The MCP server validates all inputs. The Policy Engine rejects any request that does not match the user's stated intent. |
| **Unauthorized Access** | API key authentication. All MCP requests must include a valid API key. |
| **Replay Attacks** | Idempotency keys on all payment operations. |
| **Data Leakage** | The MCP server never exposes raw payment credentials. All sensitive operations are performed server-side. |
| **Rate Limiting** | MCP requests are subject to the same rate limits as REST API requests. |

## 17. Security Architecture

### 17.1 Security Principles

- **Zero Trust:** Never trust, always verify. Every request is authenticated and authorized.
- **Least Privilege:** Users and services have only the permissions they need.
- **Defense in Depth:** Multiple layers of security controls.
- **Fail Secure:** If a security control fails, the system defaults to the most secure state.

### 17.2 Encryption

| Layer | Encryption | Algorithm |
|---|---|---|
| **In Transit** | TLS 1.3 | AES-256-GCM |
| **At Rest** | Database encryption | AES-256 |
| **API Keys** | Hashing | SHA-256 |
| **PII** | Field-level encryption | AES-256-GCM |
| **Stablecoin Keys** | HSM | FIPS 140-2 Level 3 |

### 17.3 Authentication & Authorization

| Method | Use Case | Details |
|---|---|---|

| **MFA** | Dashboard login | TOTP (Google Authenticator, Authy) |
| **HMAC** | Webhook verification | SHA-256 signature |

### 17.4 PCI-DSS Compliance

AetherPay must comply with **PCI-DSS 4.0** for card payments. Key requirements:

- **Requirement 6.4.3:** Script integrity on payment pages must be explicitly verified and managed. Scripts must be sourced from trusted providers .
- **Requirement 11.6.1:** Payment form content and header integrity monitoring .
- **Requirement 3.4:** PAN must be rendered unreadable anywhere it is stored.
- **Requirement 4.1:** Strong cryptography for transmission of cardholder data over open networks.

**Compliance Level:** AetherPay will be a **Level 1** service provider (6+ million transactions annually) .

## 19. Regulatory & Licensing Strategy

## 21. Operational Runbook

### 21.1 Rail Outage Response

| Step | Action | Owner |
|---|---|---|
| 1 | Detect: Circuit breaker opens, alert fires | Monitoring |
| 2 | Acknowledge: On-call engineer acknowledges alert | On-call |
| 3 | Assess: Check provider status page, API logs | On-call |
| 4 | Mitigate: AI routing automatically routes to backup rail | System |
| 5 | Communicate: Update status page, notify affected customers | Ops |
| 6 | Resolve: Provider restores service, circuit breaker closes | Provider |
| 7 | Post-Mortem: Document incident, update runbook | Ops |

### 21.2 Stuck Transaction Resolution

| Step | Action | Owner |
|---|---|---|
| 1 | Detect: Transaction stuck in `pending` > 30 minutes | Monitoring |
| 2 | Investigate: Check provider status, ledger entries | Ops |
| 3 | Resolve: Manual override, refund, or reversal | Ops |
| 4 | Communicate: Notify customer of resolution | Support |

### 21.3 Liquidity Crunch Escalation

| Step | Action | Owner |
|---|---|---|
| 1 | Detect: Liquidity below minimum buffer | Monitoring |
| 2 | Alert: Notify Treasury team | Slack |
| 3 | Assess: Determine cause (high volume, provider delay) | Treasury |
| 4 | Rebalance: Move funds from other corridors | Treasury |
| 5 | Communicate: Notify affected customers if delays expected | Ops |

### 21.4 Fraud Incident Response

| Step | Action | Owner |
|---|---|---|
| 1 | Detect: Fraud alert fires | Monitoring |
| 2 | Assess: Review transaction, customer profile | Compliance |
| 3 | Freeze: Freeze account if fraud confirmed | Compliance |
| 4 | Investigate: Gather evidence, file SAR if needed | Compliance |
| 5 | Resolve: Refund affected customers, update rules | Compliance |

| Step | Action | Owner |
